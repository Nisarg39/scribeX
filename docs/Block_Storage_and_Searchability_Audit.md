## 1. Actual Database Schema & Storage Mechanism

ScribeX uses a robust SQLite database architecture (fully defined in [`schema.ts`](file:///Users/nash/Documents/FrontEnd%20Development/ai_projects/scribeX/frontend/src/db/schema.ts)) designed for high performance, local-first reliability, and bidirectional round-tripping.

### SQLite Tables Overview
1. **`folders`**: Tree hierarchy for notes (`id`, `user_id`, `name`, `parent_id`, `path`, `color_token`, `icon`, `sync_rev`, `created_at`, `updated_at`).
2. **`tags`**: Unique user tags (`id`, `user_id`, `name`, `color_token`, `created_at`).
3. **`notes`**: Core document storage table with dual-representation persistence.
4. **`note_tags`**: Many-to-many junction table linking notes to tags.
5. **`tasks`**: Single source of truth ledger for tasks projected from checklist blocks or task lists (`id`, `user_id`, `note_id`, `note_title`, `note_color_token`, `block_id`, `title`, `is_completed`, `priority`, `due_date`, etc.).
6. **`assets`**: Binary asset ledger (`id`, `user_id`, `storage_key`, `file_name`, `mime_type`, `size_bytes`, `sha256_hash`, `processing_status`, `extracted_text`).
7. **`entity_relations`**: Knowledge graph connections (`source_id`, `relation_type`, `target_id`, `created_by`, `confidence_score`).
8. **`sync_changelog`**: Event-sourced delta sync changelog.

### The `notes` Table Schema
```sql
CREATE TABLE IF NOT EXISTS notes (
  id TEXT PRIMARY KEY,
  user_id TEXT NOT NULL,
  folder_id TEXT,
  folder_path TEXT,
  group_name TEXT,
  title TEXT NOT NULL,
  content_markdown TEXT NOT NULL DEFAULT '',
  blocks_json TEXT NOT NULL DEFAULT '[]',
  color_token TEXT NOT NULL DEFAULT 'apricot',
  is_favorite BOOLEAN NOT NULL DEFAULT 0,
  is_pinned BOOLEAN NOT NULL DEFAULT 0,
  status TEXT CHECK(status IN ('active', 'archived', 'trashed')) NOT NULL DEFAULT 'active',
  priority_score REAL DEFAULT 0.0,
  sync_rev INTEGER NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  trashed_at DATETIME,
  FOREIGN KEY (folder_id) REFERENCES folders(id) ON DELETE SET NULL
);
```

### The Dual-Persistence Storage Mechanism
Every note in ScribeX stores its blocks in **two concurrent places** in the `notes` table:
1. **`blocks_json`**: A JSON stringified array of `ComposableBlock` objects (`{ id, type, content, metadata }`). This serves as the precise structured AST used by the React Native / Web rich block editor.
2. **`content_markdown`**: A fully serialized Extended Markdown document generated by [`astSerializer.ts`](file:///Users/nash/Documents/FrontEnd%20Development/ai_projects/scribeX/frontend/src/core/astSerializer.ts). Complex and rich domain blocks embed structured state via HTML comment annotations (e.g., `<!-- scribex:block type=... data='...' -->` or attribute strings). This ensures human-readability, external markdown export compatibility, and robust text-searchability.

## 3. Search Architecture Recommendations & Traps

When implementing full-text search (FTS) or query filtering across notes, developers must be mindful of several architectural traps inherent in dual-persistence markdown and JSON storage:

### ⚠️ Common Search Traps
1. **Raw `content_markdown` Naive `LIKE` Searches:**
   - Searching `content_markdown` with `LIKE '%query%'` will falsely match internal HTML comment attribute keys, such as `type=bookmark`, `type=meeting_notes`, `folder="General"`, or JSON syntax punctuation (`"checked":false`, `{`, `}`, `[`).
   - Base64 data URIs embedded in images (`data:image/jpeg;base64,...`) or audio blocks can contain random alphanumeric substrings that accidentally match search queries.
2. **Raw `blocks_json` Stringified Searches:**
   - Querying `blocks_json` directly without parsing JSON treats structural keys (`"type":"code"`, `"id":"b-123"`) as searchable text, leading to noisy results.

### 💡 Recommended Search Strategy
To build a clean, lightning-fast search engine in ScribeX:
1. **Target Note-Level Fields Indexing:** Index note `title`, `folder_path`, and associated `tags` with high boosting weight.
2. **Extract Human-Readable Text from Blocks:**
   - For **Division A & B** blocks, extract `block.content` and specific human-facing metadata fields (`metadata.title`, `metadata.description`, `metadata.attendees`, `metadata.merchant`, `metadata.ocrText`, `metadata.transcription`).
   - Explicitly **exclude** base64 data payloads, file storage URIs, SVG path arrays (`metadata.paths`), and HTML comment markup wrapper syntax.
3. **Dedicated FTS5 Virtual Table / Index:** Maintain an optimized SQLite FTS5 table (`notes_fts`) populated via triggers or repository transactions that indexes only clean text tokens from note titles, folder paths, and human-readable block content/metadata.
